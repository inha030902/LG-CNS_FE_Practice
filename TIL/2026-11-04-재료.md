### 문서 — OAuth 순서 (`nextauth-oauth` 3절)
1. 버튼 클릭 → `signIn("kakao")`
2. 브라우저가 `/api/auth/signin/kakao` → 카카오 인가 화면으로 이동
3. 카카오가 `/api/auth/callback/kakao`로 돌려보냄
4. next-auth가 code를 토큰으로 바꾸고 사용자 정보를 읽음
5. `jwt` 콜백 실행 → 결과가 JWT 쿠키로 저장됨

### 문서 — 토큰이 세션이 되기까지 (`nextauth-oauth` 3~5절)
- `jwt` 콜백 전에 기본 토큰 `{ name, email, picture, sub }`이 먼저 만들어짐
- `session` 콜백은 토큰을 `accessToken`, `expiresIn`, `user.{ id, email, name, profileImageUrl }` 모양으로 다시 만듦. `token.picture`, `token.sub`는 세션에 복사하지 않음
- 이미 발급된 JWT에는 바뀐 콜백이 소급되지 않음. 콜백을 고친 뒤 확인하려면 다시 로그인해야 함
- `route.ts`, `authOptions.ts`, `next-auth.d.ts`, 로그인 버튼은 실행 시점이 모두 다름: 각각 요청이 올 때, 서버에서 import할 때, 컴파일할 때만, 브라우저에서 클릭할 때. HTML `<script>`의 `async`, `defer`와는 관계없음

- **토큰과 세션**: 이름은 `session`이지만 `strategy: "jwt"`라서 서버에 세션을 저장하지 않고, 값은 쿠키의 JWT에 있음. 일반 로그인의 `accessToken`은 무작위 문자열이고 어디서도 검증하지 않음
- **로그아웃**: `signOut()`은 우리 사이트의 세션 쿠키만 지움. 카카오·구글 계정까지 로그아웃되지는 않음. 내 `main`에는 버튼이 없어서 `/api/auth/signout`이나 `next-auth.session-token` 쿠키 삭제로 확인 가능
- **소셜 로그인과 회원가입**: 지금 코드는 회원가입 없이 소셜 로그인이 되고 DB에도 저장하지 않음. 국내 사이트는 보통 소셜 인증 → 기존 회원 확인 → 약관·추가 정보 → 저장 순서
- **기존 회원의 소셜 로그인**: 우리 회원가입은 이메일 소유를 확인하지 않으므로, 이메일이 같다고 자동 연결하면 위험함
- **세 가지 id**

| 이름 | 만드는 곳 | 의미 |
|---|---|---|
| `id` (`_id`) | MongoDB | 우리 DB의 회원 번호 |
| `userId` | 사용자 입력 | 회원가입 아이디 |
| `providerAccountId` | 카카오, 구글 | 소셜 서비스 안의 회원 번호. `provider`와 함께 봐야 구분됨 |

- 지금 `session.user.id`는 로그인 방식에 따라 DB `_id`이거나 소셜 번호임. 소셜 사용자를 DB에 저장하게 되면 항상 `_id`를 넣도록 맞춰야 함

### 코드 — `useState` → `useTransition` (`13:50`)

```tsx
const [pending, setPending] = useState(false);

const handleSubmit = (event) => {
  event.preventDefault();
```

```ts
// config/initial.ts
const withoutAuthUrlList = ["/login", "/signup"]; // 로그인하면 못 들어가는 곳
const authUrlList = ["/cart", "/order"];          // 로그인해야 들어가는 곳

function safeCallbackPath(value) {
  if (!value || !value.startsWith("/") || value.startsWith("//")) return "/";
  const pathname = value.split("?")[0];
  if (withoutAuthUrlList.includes(pathname)) return "/";
  return value;
}
```
- 외부 사이트로 보내는 주소(`https://...`, `//...`)와 로그인 페이지로 되돌아오는 주소를 걸러냄
- `includes`는 경로 전체를 비교함. `/cart/1`, `/login/extra`는 목록에 걸리지 않음

```ts
async redirect({ url, baseUrl }) {
  if (url.startsWith("/")) return `${baseUrl}${url}`;
  if (new URL(url).origin === baseUrl) return url;
  return baseUrl;
}
```

### 문서 — Proxy (`next-proxy`)
- Next.js 16에서 `middleware.ts` → `proxy.ts`, 함수 이름도 `proxy`. `app/`과 같은 높이에 둠
- 페이지를 그리기 **전에** Node.js에서 실행됨. 이름을 바꾼 이유는 Express 미들웨어와 헷갈리고, 네트워크 경계의 역할에 가깝기 때문
- `proxy`라는 이름의 export 또는 default export만 허용. `export const runtime`은 쓸 수 없음
- 실행 순서: `next.config`의 `headers`, `redirects` → `proxy` → 파일 시스템 라우트. 리다이렉트하면 페이지 컴포넌트는 실행되지 않음
- `matcher: ["/((?!api|_next/static|_next/image|favicon.ico).*)"]`: `api`, 정적 파일 등을 제외. 그래서 `/api/auth/...`는 프록시를 타지 않음. 값은 빌드 때 분석되므로 변수로 넣으면 무시됨
- `getToken`의 기본 secret은 `NEXTAUTH_SECRET`. 쿠키 이름은 `next-auth.session-token`, HTTPS면 `__Secure-` 접두사가 붙음
- **쿠키가 있다 ≠ 로그인으로 판단**: 13:57 코드는 JWT를 풀어 `accessToken`이 비어 있지 않을 때만 로그인으로 봄
- `NextResponse.redirect`의 기본 상태 코드는 307 (메서드와 본문 유지)
- **서버 함수의 권한 검사는 프록시에만 기대지 말고 서버 함수 안에서도 해야 함**. 서버 함수는 별도 URL이 아니라 그 페이지로 보내는 POST라서, 매처에서 빠지면 프록시를 타지 않음

| 시점 | 담당 |
|---|---|
| 로그인한 사람이 `/login`, `/signup` 접속 | `proxy.ts` |
| 로그인 안 한 사람이 `/cart`, `/order` 접속 | `proxy.ts` → `/login?callbackUrl=원래경로` |
| 로그인 성공 후 이동 | `signIn`의 `callbackUrl` + `callbacks.redirect` |

| 요청 (`accessToken` 있음) | 결과 |
|---|---|
| `/login?callbackUrl=/cart` | 307, `/cart` |
| `/login?callbackUrl=https://evil.example` | 307, `/` |
| `/login?callbackUrl=//evil.example` | 307, `/` |
| `/login?callbackUrl=/signup` | 307, `/` |

## 파트6~7 — Next.js 캐시 전략 (16:15~17:50)

> 녹음과 공식 문서로 정리한 내용. 오늘 커밋에는 캐시 코드가 없고, 아래 코드는 공식 문서 방식의 예시임. 직접 실행해 보지 않았음.

### 왜 캐시를 쓰는가
- 글처럼 자주 바뀌지 않는 데이터를 100만 명이 읽을 때, 매번 DB에 가면 요청도 100만 번
- Next 서버가 결과를 저장해 두면 사용자 수가 아니라 **Next 서버가 요청한 횟수**만큼만 DB에 감
- 핵심은 화면보다 **DB 부하를 줄이는 것**. 메모이제이션과 같은 발상
- 비용은 Next 서버의 메모리. 메모리 비용과 DB 비용을 비교해서 쓸지 정함. 백엔드 캐시가 이미 있으면 굳이 안 써도 됨

### 캐시의 약점과 해결: 재검증
- **DB가 바뀌어도 캐시는 모름**
- 해결 1, 시간 기준: 일정 시간이 지나면 다시 가져옴
- 해결 2, 요청 기준: 글 작성·수정도 Next를 거치므로, 변경에 성공했을 때 태그로 캐시를 무효화함
- 수업에서는 이 흐름을 이벤트 드리븐 방식에 비유함

```text
글 수정 요청 → Next 서버 → DB 저장 성공 → 해당 태그 무효화
다음 읽기 요청 → 새 데이터를 DB에서 가져와 캐시 → 이후 사용자는 캐시에서 읽음
```

### Next.js 16의 방식: Cache Components
수업에서 이전 방식으로 개념을 설명한 뒤 공식 문서로 새 방식을 함께 확인함. Next.js 16(2025-10-21 발표)에서 캐시 작성법이 `fetch` 옵션 중심에서 `"use cache"` 선언 중심으로 옮겨 감.

| | 이전 방식 | Cache Components |
|---|---|---|
| 켜기 | 별도 설정 없음 | `next.config`의 `cacheComponents: true` |
| 캐시 선언 | `fetch(url, { cache: "force-cache" })`, `fetch`가 아니면 `unstable_cache` | 함수나 컴포넌트 맨 위에 `"use cache"` |
| 유지 시간 | `fetch(url, { next: { revalidate: 60 } })` | `cacheLife("hours")` |
| 태그 | `fetch(url, { next: { tags: ["posts"] } })` | `cacheTag("posts")` |
| 캐시 키 | 직접 신경 써야 하는 경우가 있음 | 인자와 사용하는 바깥 값으로 자동 생성 |

- `"use cache"`는 함수나 훅이 아니라 `"use client"`, `"use server"` 같은 **지시어**. 함수, 컴포넌트, 파일 맨 위에 적음
- `fetch`가 아니라 함수 결과를 캐시하므로 Prisma로 DB를 직접 조회하는 우리 프로젝트에 잘 맞음. 문서도 `unstable_cache`가 `use cache`로 대체됐다고 안내함
- 지시어마다 `cacheLife`를 함께 쓰도록 문서가 권장함. 없으면 `default` 설정 적용
- 이전 방식이 없어진 것은 아님. `cacheComponents`를 켜지 않은 프로젝트용 "Previous Model" 문서가 따로 있음

```ts
// 조회: 데이터 함수에 캐시 선언 (공식 문서 방식의 예시)
import { cacheLife, cacheTag } from "next/cache";

export async function getPosts() {
  "use cache";
  cacheLife("hours");
  cacheTag("posts");
  return prisma.post.findMany(); // fetch가 아닌 DB 조회도 같은 방식
}
```
```ts
// 변경: 서버 액션에서 저장 후 태그 무효화
"use server";
import { updateTag } from "next/cache";
import { redirect } from "next/navigation";

export async function createPost(formData: FormData) {
  const post = await prisma.post.create({ /* ... */ });
  updateTag("posts");
  redirect(`/posts/${post.id}`);
}
```

| | `updateTag(tag)` | `revalidateTag(tag, "max")` | `revalidatePath(path)` |
|---|---|---|---|
| 호출 위치 | 서버 액션만 | 서버 함수, Route Handler | 서버 함수, Route Handler |
| 동작 | 즉시 만료. 다음 요청은 새 데이터를 기다림 | 일단 이전 데이터를 주고 뒤에서 갱신 | 경로 기준으로 무효화 |
| 어울리는 곳 | 내가 쓴 글이 바로 보여야 할 때 | 약간 늦어도 되는 글, 상품 목록, 웹훅 | 어떤 태그인지 모를 때. 문서는 태그 방식을 권장 |

`cacheLife` 값의 뜻: `stale`은 브라우저가 서버에 묻지 않고 쓰는 시간, `revalidate`는 지나면 뒤에서 갱신하는 시간, `expire`는 지나면 새 데이터를 기다려야 하는 시간.

| 프로필 | `stale` | `revalidate` | `expire` |
|---|---|---|---|
| `default` | 5분 | 15분 | 없음 |
| `seconds` | 30초 | 1초 | 1분 |
| `minutes` | 5분 | 1분 | 1시간 |
| `hours` | 5분 | 1시간 | 1일 |
| `days` | 5분 | 1일 | 1주 |
| `weeks` | 5분 | 1주 | 30일 |
| `max` | 5분 | 30일 | 1년 |

- `seconds`처럼 수명이 짧은 캐시는 프리렌더에서 빠지고 요청 시점에 처리됨
- 캐시하지 않은 데이터만 다시 불러오려면 서버 액션의 `refresh()`. 캐시는 건드리지 않음

### 렌더링과 연결되는 내용
- `"use cache"`의 결과는 **static shell**(미리 만든 HTML)에 들어갈 수 있고, 캐시하지 않는 부분은 `<Suspense>`로 감싸 요청 시점에 스트리밍함. 이 방식이 Partial Prerendering
- 수업의 "자주 안 바뀌는 페이지는 SSG처럼 정적으로" 설명이 여기에 해당함
- 동적 경로는 `generateStaticParams`로 일부만 미리 만들고, 나머지는 첫 방문 뒤 채움(ISR). Cache Components에서는 **최소 1개의 param을 반환**해야 함. 빈 배열은 빌드 오류
- 프리렌더 중 끝나지 않는 컴포넌트는 직접 처리해야 함: `"use cache"`, `<Suspense>`, `connection()` 중 하나
- `<Suspense>`는 데이터가 오는 동안 대체 화면을 보여 주는 완충재. 그 자체로 컴포넌트를 동적으로 만들지는 않음
- `partialPrefetching`이 켜져 있으면 `<Link>`가 페이지의 공통 틀(App Shell)을 미리 가져옴. URL 값에 따라 달라지는 캐시까지 미리 받으려면 `prefetch={true}`

### 우리 코드와 연결
- `next.config.ts`에 `cacheComponents: true`, `partialPrefetching: true`가 이미 켜져 있음 (10/29 첫 커밋부터). 즉 **새 방식이 적용되는 프로젝트**
- 아직 코드에 `"use cache"`, `cacheTag`, `revalidateTag`는 없음
- 오늘 `AuthShell`을 `<Suspense>` 안에 두고 `await connection()`을 넣은 것, 개발 화면에 뜬 Insights가 같은 규칙에서 나온 것
- 로그인 정보와 주의점: `"use cache"` 안에서는 `cookies()`, `headers()`, `searchParams`를 읽을 수 없음. 밖에서 읽어 인자로 넘기는 방식을 문서가 권장하고(인자는 캐시 키가 됨), 어렵다면 `"use cache: private"`를 씀. 인자와 태그는 평문으로 저장되므로 비밀 값을 넣으면 안 됨
- 그래서 세션을 읽는 `AuthShell`은 캐시 대상이 아니고, 글·상품 목록 같은 공통 데이터가 후보임

### 서버가 여러 대일 때
- 기본 메모리 캐시는 **Next 프로세스마다 따로** 있음. 로드밸런서 뒤에 여러 대를 두면 서버마다 캐시가 달라질 수 있음
- 서버 한 대의 메모리 캐시 크기는 `cacheMaxMemorySize`로 조절함. 기본 50MB
- 캐시는 배포 단위. 새로 배포하면 `use cache` 항목은 이어지지 않음 (캐시 키에 빌드 ID 포함)
- `revalidateTag`도 기본은 호출한 서버에만 적용됨
- 해결: `cacheHandlers`로 Redis 같은 공유 저장소 연결, 또는 `"use cache: remote"`. 문서는 대부분의 앱에는 필요 없다고 설명함
- 강사님 프로젝트 경험: Redis가 비용 문제로 안 되면 이중화 환경에서 이 기능을 포기해야 할 수 있음

### 수업 설명과 공식 문서를 함께 볼 부분
| 수업에서 들은 내용 | 공식 문서 기준 |
|---|---|
| `fetch`는 기본으로 강제 캐시 | 15부터 기본 캐시 안 함. `force-cache`로 직접 켬. Cache Components도 완전히 opt-in |
| 태그를 동작시키면 Next가 데이터를 다시 가져옴 | 호출 시점이 아니라 **다음 요청 때** 갱신이 시작됨 |
| `use cache`는 아직 베타 같은 기능 | 16.0.0에 포함, `cacheLife`·`cacheTag`는 stable, 새 프로젝트 기본값으로 켜짐. 다음 메이저에서 항상 켜지고 옵션은 사라질 예정 |
| 서버리스에서도 캐시 메모리로 가볍게 운영 | 서버리스의 메모리 캐시는 요청 사이에 유지되지 않는 경우가 많음. 직접 운영하는 서버에서는 유지됨. 빌드 시점 캐시는 정상 동작. 지속이 필요하면 `use cache: remote` |
| `revalidateTag`가 바로 안 바뀌는 문제 때문에 `updateTag`가 나온 것 같음 (강사님 추측) | 문서는 이유를 설명하지 않고 쓰임만 구분함. `revalidateTag`는 이전 데이터 먼저, `updateTag`는 즉시 만료. 인자 1개짜리 `revalidateTag(tag)`는 deprecated |

### 병렬 패칭
```ts
const [artist, albums] = await Promise.all([getArtist(id), getAlbums(id)]);
```
- `await`를 두 번 쓰면 앞의 요청이 끝나야 다음 요청이 시작됨. `Promise.all`은 동시에 시작하고 모두 끝날 때까지 기다림
- 수업 권장: 서비스 계층에서 묶어서 처리. 우리 [userService.ts](../lgcns-fe-next/service/userService.ts)의 `list`, `checkIdentity`가 이 형태
- 문서 주의점: 하나라도 실패하면 전체가 실패함. 일부 실패를 허용하려면 `Promise.allSettled`

### 그 밖에 챙길 내용
- **`fetch` 권장**: 강사님은 axios 같은 라이브러리보다 기본 `fetch` 사용을 권장함
- **공식 문서 기준으로 공부**: 책과 영상은 금방 낡음. Next는 버전에 따라 작성법이 크게 달라짐
- **성능 향상을 말할 때**: "2초 → 0.02초"만으로는 부족함. 데이터 양, 트래픽, 조건 같은 기준이 있어야 함. 포트폴리오에도 면접 질문에도 해당

## 트러블슈팅 후보

### 1. 카카오 로그인 후 로그인 안 된 상태로 표시됨
- **문제**: 로그인 후에도 `{ accessToken: '', isLoggedIn: false }`, `/login`에 머무름
- **원인**: 당시 코드는 카카오 로그인에도 `accessToken`을 넣지 않는데, 화면은 `accessToken` 유무로 로그인을 판단함
- **해결**: `AuthShell`에서 `isLoggedIn={Boolean(session)}`로 변경
- **배운 점**: 세션 존재와 `accessToken` 존재는 다른 조건임

### 2. 구글 로그인의 `accessToken`이 사라짐
- **문제**: 구글 분기에서 넣은 값이 비어 버림
- **원인**: 구글 분기에 `return`이 없어서 아래 `if (user)`가 `undefined`로 덮어씀 (문서 `next-proxy` 4절)
- **해결**: 강사님은 분기 안에서 `return`(step4), 내 `main`은 `proxy.ts`를 `Boolean(token)`으로 판단하게 변경

### 3. 브랜치 전환 후 필기가 사라짐, Lesson Replay가 켜지지 않음
- **문제**: step4로 옮기자 `필기/`, `TIL/` 파일이 사라지고 빈 필기가 생김. 기록도 실패함
- **원인**: 두 폴더는 내 `main`에만 있음. 또 step4 `LoginForm.tsx:35`의 lint 오류(`react-hooks/set-state-in-effect`)가 husky pre-commit을 막음
- **해결**: `main`으로 복귀. 앞으로 필기와 기록은 `main`에서만 작성
- **배운 점**: 브랜치를 옮기면 커밋된 파일 자체가 작업 폴더에서 바뀌거나 빠짐. `docs/`도 브랜치마다 다름

### 4. step4에서 일반 로그인이 비로그인으로 처리됨
- **문제**: 로그인 응답은 200이지만 세션의 `id`, `accessToken`이 빈 값. `/cart`로 가면 다시 `/login`
- **원인**: `14:30` 커밋에서 `if (user)` 블록이 삭제되어 일반 로그인 값을 토큰에 넣는 코드가 없어짐
- **상태**: step4 서버에서 `curl`로 직접 확인함. 고치지 않음
- **해결 방향**: `return token` 앞에 `if (user)` 블록 복원

### 5. 아직 원인을 모르는 것
- 두 번째 카카오 콜백에서 `State cookie was missing` 발생. 뒤로 가기·새로고침·재시도 때문일 수 있으나 확인하지 못함
