### 코드 — 버튼 hover 테두리 애니메이션 (`App.css`)
```css
@property --orbit {            /* 각도를 애니메이션할 수 있는 CSS 변수 */
  syntax: "<angle>";
  inherits: false;
  initial-value: 0deg;
}

.counter::before {
  background: conic-gradient(from var(--orbit), transparent 0deg, transparent 230deg,
              #ff9af5 300deg, #fff 332deg, #ff00fb 360deg);
  opacity: 0;
  transition: opacity 0.25s ease;   /* 나타날 때 부드럽게 */
}
.counter:hover::before {
  opacity: 1;
  animation: counter-orbit 1.2s linear infinite;
}

@keyframes counter-orbit {
  to { --orbit: 1turn; }
}

@media (prefers-reduced-motion: reduce) {   /* 움직임 줄이기 설정한 사용자 배려 */
  .counter:hover::before { animation: none; }
}
```

### 🔍 보충할 것
- transition과 animation의 차이: 상태 변화 사이를 보간 vs keyframes로 정의한 움직임
- 모바일 우선(`min-width`)과 데스크톱 우선(`max-width`) media 쿼리 비교
- box model: content → padding → border → margin

### 1. 오늘 소셜 아이콘 코드를 설계한 순서
1. **공통 패턴 찾기** → 4개 링크가 같은 형태라서 컴포넌트로 만들기로 함
2. **SVG를 컴포넌트로** → SVG를 텍스트(데이터)로 다루기는 애매해서 아이콘 자체를 컴포넌트화 (`svg/GitHubIcon.tsx` 등)
3. **단일 항목 UI 만들기** → 들어가는 값은 아이콘, 이름, 링크(URL) 정도 (`SocialIconItem`)
4. **반복 처리** → 데이터(`socialData`)를 불러와서 `map`으로 풀기 (`SocialIconList`)
5. **최종 목표** → `socialData`가 나중에 **DB에서 오는 형태**가 되면 프론트엔드의 기본 틀이 완성됨

- 아이콘 컴포넌트에는 아직 props를 정의하지 않았음. `size`, `color`, `className` 같은 props를 받게 만들면, 기본값과 주어진 값으로 **어디서든 크기·색을 바꿔서** 재사용할 수 있음.
- 실무(SI)에서는 귀찮아서 TSX에 하드코딩하는 경우가 많음. 유지보수하기 좋고 관리 체계가 있는 코드를 짜는 게 경쟁력.

### 2. map / filter / slice 체이닝
- `map`, `filter`, `slice`를 이어서(체이닝) 쓸 수 있음
  ```tsx
  socialData
    .filter((s) => s.name !== 'X.com')   // 조건에 맞는 것만
    .slice(0, 3)                          // 앞에서 3개만
    .map((s) => <SocialIconItem key={s.id} social={s} />)
  ```
- **되도록 심플하게 쓰기.** 자꾸 변형하려고 하지 말 것.
- map이 익숙하지 않으면 몇 번 직접 써 보면 됨.

### 3. Q&A — 데이터로 관리할 것과 아닌 것
- **Q. 아이콘을 컴포넌트로 import하는데, API(DB)로 받으면 컴포넌트를 담을 수 없지 않나?**
  - 맞음. 아이콘을 DB에 저장할 이유는 거의 없음.
  - 꼭 데이터로 관리해야 한다면: SVG 파일을 파일 서버(스토리지)에 올리고 **URL만 DB에 저장** → `<img src={url}>`로 표시
  - 다른 방법: 데이터에는 `'github'` 같은 문자열 키만 두고, 프론트에서 키 → 아이콘 컴포넌트로 매핑
- **DB화하는 기준:** 반복되는 항목이 아주 많을 때. 아니면 지금처럼 **초기 데이터(initial data) 파일**로 빼서 import하는 걸로 충분함.
- 이런 방식이 잘 맞는 곳: **헤더 메뉴** (1depth, 2depth, 3depth 서브 메뉴를 하드코딩하면 코드가 너무 복잡해짐)
- 어떤 방식이 나은지 AI한테 물어보고 같이 토의하는 것도 방법

### 4. Q&A — 폴더 구조
- `lib/` = library. 프로젝트 안에서 **내가 라이브러리처럼 만든 것**을 넣는 곳 (npm으로 받은 패키지를 넣는 곳이 아님)
- `components/`로 끝내지 않고 안에서 `ui/`, 액션 등으로 나눔
- React는 정해진 구조가 없어서 자유. Next.js는 `app/` 디렉토리 규칙이 있어서 아무 폴더나 만들면 안 됨.
- 기능별로 나눌지, 아키텍처(레이어)별로 나눌지에 따라 달라짐. 회사에 가면 회사 규칙을 따르면 됨.
- **래퍼(wrapper) 컴포넌트**: `section`, `div` 같은 묶음 태그를 그대로 쓰지 않고 `<Section>` 같은 컴포넌트로 만들어 관리하는 방식도 있음
- 이름에 집착하지 말고 **구조의 전체 흐름**을 이해할 것
- 내일·모레쯤 **아토믹(Atomic) 디자인** 설명 예정 → 거기에 맞는 폴더 용어가 있음

### 5. Q&A — useState와 useEffect
- **state** = 상황. **useEffect** = 트리거(방아쇠).
- 비유: 캔 음료
  - 버튼을 눌러서 뚜껑을 따는 것처럼 **사용자 행동으로 바뀌는 건 effect가 필요 없음** (이벤트 핸들러로 처리)
  - "자판기에서 나오자마자 자동으로 뚜껑이 열려야 한다"처럼 **어떤 상황이 되면 자동으로 일어나야 하는 것**에 useEffect를 씀
  - 연쇄 반응: 컵에 물이 따라지기 시작하면 → 다음 동작 → 또 다음 동작
- **dependency 배열** = "이게 바뀌면 감지하겠다"
- 열린다/닫힌다는 **mount / unmount**(컴포넌트가 화면에 붙었는지, 떨어졌는지)라는 개념이 따로 있음. 상태 변화와 비슷하지만 조금 다른 의미.
- state와 effect를 잔뜩 써서 만드는 코드는 문제가 많아서, **Next.js로 가면 이 방식을 많이 바꿈**

### 6. AI 활용에 대해
- 강사님이 보여주는 컴포넌트 코드를 빨리 만드는 건 AI가 써 주기 때문. TypeScript의 귀찮은 부분도 AI가 많이 도와줌.
- **잘 정제된 샘플 코드를 갖고 있으면** AI가 그 수준으로 코드를 써 줌. 정제 안 된 코드를 주면 그 수준에 맞춰서 만듦. → 오늘 받은 코드를 샘플로 잘 보관하기
- 강사님은 "git add + commit + push + PR 메시지 작성"을 하나의 명령어로 묶어 AI 규칙(md 파일)으로 등록해서 씀
- 회사에서 AI 에이전트를 쓰면 어디에 쓰는지, 무엇을 검색하는지 다 기록되니 조심
