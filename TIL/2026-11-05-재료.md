```json

{
  "semi": true,
  "singleQuote": false,
```

- 세 값 모두 Prettier 3.9의 기본값과 같음. 기본값을 파일에 적어 둔 것 (문서 `prettier` 2절)

- 13:29 커밋의 변경 파일이 많은 이유 중 하나가 이 포맷 적용. 코드 변경이 아니라 줄바꿈과 따옴표만 바뀐 파일도 섞여 있음 (diff 양으로 추정)

### 🔍 보충할 것 — ORM과 JPA
- 필기에는 단어만 있음
- ORM: 테이블(또는 컬렉션)과 코드의 객체를 연결해서, 쿼리를 직접 쓰지 않고 객체 메서드로 다루는 방식
- JPA: Java 진영의 ORM 표준 명세. 구현체로 Hibernate가 대표적
- 우리 프로젝트의 `prisma.post.findMany(...)`가 같은 역할. Prisma는 TypeScript 쪽 ORM으로, 지금은 MongoDB에 연결되어 있음

## 파트2 — 캐시를 쓰는 이유, 수정과 삭제 (10:30~11:30)

### 필기
- CRUD 중 C, U, D는 write, R은 read 관련. cache → read. cache를 사용해야 하는 이유를 알아야 함 (10:14~10:22)
- Event Driven Architecture 정의와 MSA에서 중요함, CDC (10:23~10:44)
- 관리체계를 만들기 위해선 `()` 사용. 디렉토리가 아님 (11:18)
- Update는 일부분만 바꾸는 것이 아니고, CRUD에서 U는 C, 즉 CREATE랑 거의 동일한 개념. 글을 수정하고 쓰는 것은 동일한 것. 다른 건 PK 값이 있냐 없냐 차이 (11:25)
- Modal과 Popup 차이. Modal은 종류가 2개: 백그라운드를 클릭 가능하게 할지 안 할지 (11:29)
- Delete는 엄밀히 봐야 함. 반드시 사용자에게 확인하게 하는 절차가 필요함 (11:29~11:30)

### 코드 — `()` 폴더 = 라우트 그룹
```text
app/(auth)/login      → /login
app/(post)/posts      → /posts
app/(post)/(postsys)/postwrite → /postwrite
```
- `(auth)`, `(main)`, `(post)`, `(postsys)`는 URL에 들어가지 않고 레이아웃만 나눔 (문서 `next-applied` 3절)
- 필기의 "디렉토리가 아님"은 이것을 말한 것으로 해석함. 폴더 모양이지만 URL 경로는 아니라는 뜻

### 코드 — 작성과 수정은 한 화면
```tsx
// app/(post)/(postsys)/postwrite/page.tsx
if (!postId) {
  return <PostEditor action={createPost} submitLabel="올리기" />;
}
const post = await getCachedPost(postId);
if (!post) redirect("/posts");
if (post.authorId !== user.id) redirect(`/postdetail/${postId}`);
return (
  <PostEditor
    action={updatePost}
    submitLabel="수정하기"
    initialHtml={post.body}
    postId={post.id}
  />
);
```
```tsx
// component/organisms/PostEditor.tsx
{postId ? <input type="hidden" name="postId" value={postId} /> : null}
<input type="hidden" name="body" value={html} />
```
- 필기의 "다른 건 PK 값이 있냐 없냐"가 코드에 그대로 있음. `postId` 유무로 제목, 액션, 버튼 문구만 갈림
- 수정할 때 바꾼 글자만 보내지 않고 본문 전체를 다시 보냄. 다만 DB 쪽은 `data: { body }`라서 `authorId`, `createdAt`은 그대로 유지됨

### 코드 — Delete 확인 절차
```tsx
// component/organisms/PostCard.tsx
<form
  action={deletePost}
  onSubmit={(event) => {
    if (!window.confirm("이 글을 삭제할까요?")) event.preventDefault();
  }}
>
```
- 취소하면 `preventDefault`로 서버 액션이 호출되지 않음
- 서버에서도 한 번 더 막음. `postService.deletePost`가 작성자가 아니면 `forbidden`을 돌려줌
- 삭제 순서는 댓글 → 좋아요 → 글. 트랜잭션은 아님 (문서 `next-applied` 8절)
- 지금 코드의 확인창은 직접 만든 Modal이 아니라 브라우저 기본 `confirm`

### 🔍 보충할 것
- **Event Driven Architecture**: 서비스끼리 직접 호출하는 대신, "글이 작성됨" 같은 이벤트를 발행하고 필요한 쪽이 구독해서 처리하는 구조. 서비스가 나뉜 MSA에서는 서로의 결합을 줄이는 데 쓰임
- **CDC(Change Data Capture)**: DB의 변경을 감지해서 다른 시스템으로 전달하는 방식. 예를 들어 DB 변경을 받아 캐시나 검색 인덱스를 갱신할 수 있음
- 우리 코드의 `updateTag("posts")`는 액션 코드가 쓰기 직후 직접 캐시를 지우는 방식이라 EDA, CDC와는 다름. 위 둘을 구현한 코드는 저장소에 없음
- **Modal 2종류**: 뒤를 못 누르게 막는 modal과, 뒤를 계속 쓸 수 있는 modeless로 부름. Popup과의 차이는 수업에서 어떻게 구분하셨는지 필기에 없음
- **U와 C**: HTTP의 PUT(전체 교체)과 PATCH(일부 변경)까지 같이 찾아보면 "Update는 일부만 바꾸는 것이 아니다"를 더 정확히 쓸 수 있음

## 파트3 — 캐시 적용과 성능 비교 (13:00~13:45)

### 필기
- cache 유무에 따른 성능 비교 필수. 단, 단편적인 성능 비교는 오히려 안 좋음. 예를 들어 "CSR vs SSR" 이 정도면 절대 안 됨 (13:42)
- 글쓰기와 수정하기의 차이. 똑같은 postwrite이지만 수정하기는 id를 받아옴 (13:51)

### 코드 — 캐시 경계 (`13:29 feat: cache component`)
```ts
// lib/postCache.ts (현재 코드)
export async function getCachedPosts(
  pageNumber: number,
  sortOrder: "ASC" | "DESC",
): Promise<PostListResponseType> {
  "use cache";
  cacheTag("posts");
  cacheLife("max");
  return postService.listPosts(pageNumber, sortOrder);
}
```
- 인자 `pageNumber`, `sortOrder`, `postId`가 캐시 키에 들어감. 1페이지 최신순과 2페이지 오래된순은 다른 항목 (문서 `posts-cache-auth` 3.1절)
- `cacheLife("max")`: stale 5분, 재검증 30일, 만료 1년
- 글 본문의 `createdAt`을 ISO 문자열로 바꿔서 돌려줌. `use cache`의 반환값은 직렬화할 수 있어야 함

### 코드 — 쓰기가 성공하면 태그를 비움
```ts
// actions/postActions.ts
export async function createPost(formData: FormData) {
  const user = await author("/postwrite");
  const result = await postService.createPost({
    authorId: user.id,
    authorName: user.name,
    body: String(formData.get("body") ?? ""),
  });
  if (!result.ok) return;
  updateTag("posts");
  redirect(`/postdetail/${result.id}`);
}
```
- 작성, 수정, 삭제, 좋아요, 댓글 다섯 군데 모두 성공한 뒤에만 `updateTag("posts")`
- `redirect`는 예외를 던져 함수를 끝내므로, 태그를 비우는 코드가 그보다 앞에 있어야 함
- `updateTag`: Server Action 전용. 다음 요청이 새 데이터를 기다림. 내가 방금 쓴 값을 바로 봐야 할 때
- `revalidateTag(tag, "max")`: Route Handler에서도 가능. 이전 값을 보여 주면서 뒤에서 갱신. 약간 늦어도 될 때

### 코드 — 사용자별 값은 캐시 밖에
```tsx
// component/organisms/PostListSection.tsx
const [user, data] = await Promise.all([readCurrentUser(), postList]);
const viewerId = user?.id ?? null;
// ...
canManage={post.authorId === viewerId}
```
- `"use cache"` 안에서는 `cookies()`, `headers()`, `searchParams`를 읽을 수 없음
- 캐시에는 모두에게 같은 글 데이터만 넣고, "내 글인가"는 캐시 밖에서 계산함
- `searchParams`도 캐시 밖 `PostsContent`에서 읽어 숫자와 `"ASC" | "DESC"`로 바꾼 뒤 인자로 넘김

### 문서 — 언제 캐시가 효과가 있나 (`post-cache-scale`)
필기의 "단편적 비교는 안 좋다"를 숫자로 보여 주는 문서. **쓰기 빈도에 따라 같은 캐시의 효과가 완전히 달라짐.**

| 조건 | 쓰기 / 분 | 글 읽기 라운드 / 분 | 추정 월 비용 |
|---|---|---|---|
| 느린 캐시 | 10 | 약 780 | 약 22만 원 |
| 빠른 캐시 (지금 코드) | 5,000 | 약 30,000 | 약 104만 원 |
| 캐시 없음 | 5,000 | 약 30,000 | 약 104만 원 |
| 빠른 쓰기 + 6초마다 한 번만 무효화 | 5,000 | 약 780 | M10으로 단정하지 않음 |

- 가정: 사용자 1만 명, 글 1만 개, 활성 사용자 5,000명이 1분에 목록과 상세를 한 번씩 열람. 서버 프로세스 1개
- 쓰기가 잦으면 캐시가 더 느려지는 것이 아니라, **DB에 가는 횟수가 캐시가 없을 때와 같아짐**
- 원인은 태그가 `"posts"` 하나뿐이라서. 다른 글의 좋아요 한 번도 내가 보던 글의 캐시까지 지움
- 무효화를 묶으면 읽기는 줄지만 쓰기 5,000번은 그대로이고, 사용자는 최대 6초 전 값을 봄. 이 배치는 현재 코드에 없음
- 읽기 복제본은 캐시 히트를 빠르게 만들지 않음. 미스가 난 읽기의 위치만 옮기고, 복제 지연이 생김
- 문서가 직접 밝히듯 **코드 모양으로 센 추정치**이고 부하 테스트 결과가 아님. 실측은 로컬 `GET /posts` 3번뿐으로, 첫 요청만 함수 본문 로그가 새 시각으로 찍히고 나머지는 `Cache` 접두로 재생됨

### 코드 — 로그인 토큰을 실제 JWT로 (`lib/accessJwt.ts`)
```ts
return new SignJWT({ email: user.email, name: user.name })
  .setProtectedHeader({ alg: "HS256" })
  .setSubject(user.id)
  .setIssuedAt()
  .setExpirationTime(`${EXPIRES_IN_SECONDS}s`)
  .sign(secret());
```
- 예전의 `randomBytes` 임의 문자열은 서명이 없어서 이제 `verifyAccessToken`이 거절함
- 만료 2시간으로 NextAuth `session.maxAge`와 같음
- 일반·카카오·구글 로그인이 모두 같은 `signAccessToken`으로 발급함. 카카오·구글의 access token은 세션에 넣지 않음
- `proxy.ts`, `AuthShell`, `readCurrentUser` 세 곳에서 서명을 검증함
- 글 폼은 사용자 아이디를 보내지 않음. 서버가 토큰의 `sub`로 사용자를 찾기 때문에, 폼을 조작해도 다른 사람 이름으로 쓸 수 없음

### 코드 — 소셜 계정 연결 (`userService.linkSocialAccount`)
1. `provider + providerAccountId`로 `Account`를 찾으면 그 `User`를 씀
2. 없고 이메일이 있으면, 그 이메일의 `User`에 `Account`만 추가
3. 둘 다 없으면 `User`와 `Account`를 함께 만듦. `password`는 넣지 않음

- 그래서 스키마의 `User.password`가 `String?`이 되었고, 비밀번호가 없는 소셜 전용 회원은 일반 로그인으로 들어오지 못함
- 2번 덕분에 같은 이메일로 일반 가입과 소셜 로그인을 해도 회원이 둘로 나뉘지 않음

### 🔍 보충할 것 — offset과 cursor
| | offset (`skip`/`take`) | cursor |
|---|---|---|
| 요청 방식 | "21번째부터 20개" | "이 글 다음부터 20개" |
| 페이지 번호로 바로 이동 | 가능 | 어려움 |
| 뒤 페이지 성능 | 앞을 건너뛰느라 느려질 수 있음 | 인덱스를 타면 일정한 편 |
| 보는 중 새 글이 생기면 | 글이 밀려 중복되거나 빠질 수 있음 | 기준점이 있어 덜 흔들림 |
| 어울리는 화면 | 게시판 | 무한 스크롤, 피드 |

- 위 표는 일반 지식이니 공식 문서로 확인할 것. Prisma에는 `cursor` 옵션이 있음
- "동시 적용 방식"은 어떤 조합을 말씀하셨는지 필기에 없음. 기억나는 대로 채울 것

### 코드 — `useOptimistic` (`17:00 feat: cache and optimistic`)
```tsx
// component/organisms/PostCard.tsx
function applyLike(current: { count: number; liked: boolean }, nextLiked: boolean) {
  if (nextLiked === current.liked) return current;
  return {
    liked: nextLiked,
    count: Math.max(0, current.count + (nextLiked ? 1 : -1)),
  };
}

function LikeButton({ postId, count, liked }) {
  const [like, setLike] = useOptimistic({ count, liked }, applyLike);

  return (
    <form
      action={async (formData) => {
        setLike(!like.liked);
        await toggleLike(formData);
      }}
    >
      <input type="hidden" name="postId" value={postId} />
      <LikeSubmit count={like.count} liked={like.liked} />
    </form>
  );
}
```
흐름:
1. 버튼을 누르면 `setLike`로 숫자와 색이 **먼저** 바뀜
2. `await toggleLike`가 서버에 저장하고 `updateTag("posts")`로 캐시를 비움
3. 액션이 끝나면 낙관적 값이 사라지고 서버가 다시 그린 `count`, `liked`로 돌아감
4. 실패해서 props가 그대로면 누르기 전 숫자로 돌아감. 별도의 오류 안내는 없음

- `useOptimistic`은 폼 액션 transition 동안만 유지되는 임시 값. `useState`처럼 값이 계속 남지 않음
- `LikeSubmit`을 자식으로 분리한 이유: `useFormStatus`는 **자기를 감싼 폼**의 상태를 읽기 때문. `pending` 동안 `disabled`라서 중복 제출도 막음
- `aria-pressed={liked}`로 눌림 상태를 스크린리더에도 알림

## 오전 문서 — 파일이 언제 실행되는가

오늘 문서 대부분이 같은 표로 시작함. **`<script async/defer/module>`과 Next 지시어를 헷갈리지 말 것.**

| 코드 | 어디서 실행 | 언제 |
|---|---|---|
| `proxy.ts` | 서버 | 페이지를 그리기 전, 매칭된 요청마다 |
| 지시어 없는 컴포넌트 | 서버 | 렌더할 때. 함수 본문의 JS는 브라우저로 안 내려감 |
| `"use cache"` 함수 | 서버 | 캐시 미스일 때만 본문 실행 |
| `"use server"` 파일 | 서버 | 폼을 POST할 때. 클라이언트는 함수 참조만 가짐 |
| `"use client"` 컴포넌트 | 서버에서 렌더 후 브라우저에서 hydrate | 번들을 받은 뒤 |
| `useEffect` 안의 `await import("quill")` | 브라우저 | 마운트 뒤 별도 청크로 받음 |

- HTML 쪽: `async`는 받자마자 실행하고 순서가 없음. `defer`는 파싱 후 순서대로. `type="module"`은 기본이 지연 실행이고 `import`/`export` 사용
- `"use client"`는 `<script type="module">`이 아니라 번들러 지시문. 함수의 `async`도 HTML `async` 속성과 이름만 같음

### Quill을 `useEffect` 안에서 import하는 이유 (`PostEditor.tsx`)
- 서버 렌더에는 `document`가 없어서 생성자를 호출할 수 없음
- `QuillBox`를 `memo`로 감쌈. 입력마다 부모 state가 바뀌어도 에디터 DOM을 React가 다시 비우지 않게 함
- `onChange`는 ref에 넣어 effect가 다시 돌지 않게 함
- 글 내용은 `getSemanticHTML()`로 숨은 input `body`에 넣어 폼으로 보냄

### 저장되는 HTML (`lib/postHtml.ts`)
- 서버의 `sanitizePostHtml`이 허용한 태그만 남긴 뒤 저장. 링크 스킴은 `http`, `https`, `mailto`만
- 상세 화면만 `dangerouslySetInnerHTML`로 그림. 목록은 태그를 벗긴 140자 텍스트
- 댓글은 정제하지 않지만 React 텍스트로 그려서 이스케이프됨

### 역할 나누기 (`.cursor/rules`)
- Action: `FormData` 읽기, service 호출, `updateTag`, `redirect`
- Service: 검증, 권한, Prisma. `redirect`, `cookies`, `FormData`를 쓰지 않음
- Prisma는 `lib/prisma.ts`와 `service/`에서만 import
- 아토믹: atom, molecule은 action을 import하지 않고, organism이 연결함

### 그 외 문서
- `react-tailwind-vite`: `tailwind.config.js` 없이 Vite 플러그인과 `@import "tailwindcss"` 한 줄로 사용. Tailwind는 브라우저가 아니라 빌드 때 소스의 클래스 이름을 찾음. 레이어 순서는 `theme, base, components, utilities`이고 뒤가 강함
- `login-signup-design`: 최대 484px 카드, 강조색 `#2563eb`. 레이어 없는 CSS가 `@layer` 안의 유틸리티보다 강해서 `globals.css`의 `h1` 규칙을 이기려고 `!font-sans`를 씀
- 가입 단계: 단계 값을 쿠키나 `localStorage`에 두지 않고, hidden input과 `useActionState` 상태로 넘김. `useOptimistic`으로 단계를 먼저 옮김 (`next-applied` 6절)
- `next.config.ts`의 `bodySizeLimit: "6mb"`: 프로필 사진 5MB와 다른 폼 값을 한 요청에 보내려고 기본 1MB에서 올림
