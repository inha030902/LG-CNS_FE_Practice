### 🔍 보충할 것 — 실시간을 받는 방식들
| 방식 | 방향 | 연결 | 이 프로젝트 |
|---|---|---|---|
| polling | 클라이언트가 주기적으로 물어봄 | 매번 새 요청 | 10:37 알림 첫 버전, 글 목록의 `PostLiveRefresh`(5초 `router.refresh`) |
| SSE (Server-Sent Events) | 서버 → 클라이언트 한 방향 | HTTP 연결 하나를 열어 두고 서버가 계속 씀 | 13:01부터 알림 |
| WebSocket | 양방향(필기의 "c→c"는 클라이언트끼리 서버를 거쳐 주고받는 채팅 같은 경우로 보임) | 처음에 HTTP로 시작해 별도 프로토콜로 바꿈 | 없음. 월요일 채팅에서 후보 |
| 푸시 알림 | 서버 → 브라우저/OS (탭이 닫혀 있어도) | 서비스 워커 + Push API, 사용자 권한 필요 | 없음 |

- **CDC (Change Data Capture)**: DB에서 바뀐 내용을 이벤트로 받아 다른 곳에 흘려보내는 방식. 이 프로젝트에서는 MongoDB **change stream**이 그 역할(파트3)
- **MongoDB cluster / 레플리카 셋**: change stream은 레플리카 셋(여러 서버가 같은 데이터를 복제)에서만 동작함. 단독(standalone) `mongod`에서는 안 열림. Atlas는 기본이 레플리카 셋

### 코드 — 알림이 생기는 조건 (`service/postService.ts`의 `notifyAuthor`)
```ts
async function notifyAuthor(input: { ...; kind: "like" | "comment" | "reply" | "commentLike"; commentId?: string }) {
  if (input.authorId === input.actorId) return; // 내 글에 내가 한 행동은 알림 없음
  await prisma.notification.create({ data: { recipientId: input.authorId, ... } });
}
```
| 행동 | 받는 사람 | `kind` | 취소하면 |
|---|---|---|---|
| 글 좋아요 | 글쓴이 | `like` | 좋아요 취소 시 그 알림 `deleteMany` |
| 댓글 | 글쓴이 | `comment` | 댓글 삭제 알림은 없음 |
| 답글 | 원 댓글 작성자 | `reply` | - |
| 댓글 좋아요 | 댓글 작성자 | `commentLike` | 취소 시 그 알림 `deleteMany` |

- 답글을 달면 원 댓글 작성자에게 `reply`가 가고, 글쓴이가 원 댓글 작성자와 다를 때만 글쓴이에게 `comment`가 감. 같은 사람에게 두 번 가지 않게
- 답글의 답글은 막음: 부모 댓글에 `parentId`가 있으면 `invalid`. 답글은 한 단계만

### 코드 — 서버: SSE 라우트 (`app/api/notifications/stream/route.ts`)
```ts
export async function GET(request: Request) {
  await connection();
  const user = await readCurrentUser();
  if (!user) return new Response(null, { status: 401 });
  // ReadableStream으로 아래를 차례로 씀
  // 1) "retry: 10000\n\n"   끊기면 10초 뒤 다시 연결하라는 지시
  // 2) subscribe(user.id, ...) 내 알림만 받는 리스너 등록. 준비 전 이벤트는 pending에 모음
  // 3) whenReady() 후 listForUser 결과를 { type: "snapshot" }으로 보냄, pending도 보냄
  // 4) 25초마다 ": ping\n\n"  연결 유지용 주석. onmessage로 올라가지 않음
  request.signal.addEventListener("abort", cleanup); // 탭을 닫으면 구독 해제
  return new Response(stream, { headers: {
    "Content-Type": "text/event-stream; charset=utf-8",
    "Cache-Control": "no-cache, no-transform",
    "X-Accel-Buffering": "no",
  }});
}
```
- SSE 메시지 형식은 `data: ...\n\n`. 빈 줄 두 개가 메시지 하나의 끝

### 코드 — 서버: change stream 하나를 모두가 나눠 씀 (`service/notificationWatch.ts`)
- `MongoClient`로 `Notification` 컬렉션을 `watch`. 옵션 `fullDocument: "updateLookup"`, `fullDocumentBeforeChange: "whenAvailable"`

## 파트5 — SSE에서 프론트가 주의할 점 (15:15~16:00)

### 필기 (15:31)
- SSE 동작 방식에서 프론트가 주의할 점: **SSE가 무한정 붙지 않게** 해야 함 (`NotificationStream.tsx` 코드 설명)
- SSE의 `EventSource`는 Authorization 헤더를 쓰지 못함. 그 이유를 알아야 함. 더 공부 필요!
- SSE는 만능이 아님

### 코드 — 무한정 붙지 않게 하는 장치 (`NotificationStream.tsx`)
```tsx
useEffect(() => {
  if (!enabled) return;                       // 로그인 + 목록이 있을 때만
  let source: EventSource | null = null;
  const open = () => {
    if (source || document.visibilityState !== "visible") return; // 이미 열렸거나 탭이 숨었으면 안 엶
    source = new EventSource(STREAM_URL);
    source.onmessage = (message) => { const event = parseEvent(message.data); if (event) onEvent(event); };
  };
  const close = () => { source?.close(); source = null; };
  const onVisibility = () => (document.visibilityState === "visible" ? open() : close());
  open();
  document.addEventListener("visibilitychange", onVisibility);
  return () => { document.removeEventListener("visibilitychange", onVisibility); close(); }; // 언마운트 시 닫기
}, [enabled, onEvent]);
```
| 장치 | 막는 것 |
|---|---|
| `if (source ...) return` | 한 컴포넌트가 연결을 두 개 여는 것 |
| 탭이 숨으면 `close`, 보이면 `open` | 안 보는 탭이 서버 연결을 계속 잡고 있는 것 |
| effect 정리 함수에서 `close` | 페이지를 떠난 뒤에도 연결이 남는 것 |
| `enabled` | 비로그인 사용자가 401을 받으며 계속 재연결하는 것 |
| 서버 `retry: 10000` | 끊겼을 때 너무 자주 재연결하는 것 |
| 서버 `abort` → `cleanup` | 서버 쪽 리스너와 ping 타이머가 남는 것 |
| change stream 하나를 공유 | 접속자 수만큼 DB 커서가 생기는 것 |

- `onEvent`는 `NotificationMenu`에서 `useCallback`으로 감싸 둠. 안 감싸면 렌더마다 새 함수 → effect 의존성이 바뀜 → 연결을 닫았다 다시 엶. **`useCallback`이 필요한 실제 예**

### 🔍 보충할 것 — 왜 `EventSource`는 Authorization 헤더를 못 쓰나
- `EventSource` 생성자는 `new EventSource(url, { withCredentials })`만 받음. 헤더를 넣는 옵션이 표준에 없음. 브라우저가 알아서 만드는 단순 GET 요청이기 때문
- 그래서 인증 방법은 보통 셋: ① 같은 출처의 쿠키(브라우저가 자동으로 실어 보냄) ② 주소 쿼리에 토큰(로그·기록에 남아 위험) ③ `fetch` + `ReadableStream`으로 SSE를 직접 읽기(헤더 가능, 대신 재연결을 직접 구현)
- **이 프로젝트는 ①**: `lgcns-fe-next`는 같은 출처라 next-auth 세션 쿠키가 자동으로 가고, 라우트가 `readCurrentUser()`로 확인함
- 반대로 `lgcns-fe`(Vite, 다른 출처)는 `fetch`에 `authHeaders()`로 Bearer 토큰을 붙이는 방식이라, 같은 SSE를 쓰려면 이 제약에 걸림. 월요일 채팅 기능에서 SSE냐 WebSocket이냐를 고를 때 고려할 점
- **SSE가 만능이 아닌 이유(일반 지식)**: 서버 → 클라이언트 한 방향뿐(채팅 보내기는 따로 요청), 연결 하나가 서버 자원을 계속 잡음, HTTP/1.1에서는 브라우저가 출처당 동시 연결 수(보통 6개)를 제한해서 탭을 여러 개 열면 막힐 수 있음, 프록시가 응답을 모아 두면 늦게 도착함(그래서 `X-Accel-Buffering: no`, `no-transform`)

- `params`, `searchParams`는 Next만의 것이 아님. React에서는 React Router가 같은 역할. 그래서 Next를 배워도 React와 겹치는 부분이 많음
- 월요일 최종본은 같은 기능을 **Next, HTML, React(Vite)** 3가지로 주는 것이 목표. 컴포넌트는 가장 보편적인 **아토믹 디자인**(atoms → molecules → organisms → templates)으로 설계
  - 이 프로젝트의 `component/atoms`, `molecules`, `organisms`, `templates` 폴더가 바로 그 구조

### 3. React(CSR)와 Next(SSR) — 보안과 디버깅
- **React 버전(`lgcns-fe`)을 화면에서 보여 줌**
  - 네트워크 탭에 로그인 요청과 응답이 그대로 다 보임
  - 서버가 아니라서 서버 로그가 없음. 콘솔에 찍지 않으면 왜 멈췄는지 모르고, 흰 화면만 뜸
  - `src/pages/Posts.tsx` 등에 `useState`와 `useEffect`, `try/catch`가 잔뜩 있음("스테이트 지옥")
  - Next식 코드를 React로 옮기다 보니 더 꼬였다고 함. 다시 React답게 마이그레이션할 예정
- **프론트엔드가 보안 취약점이 가장 많이 나오는 곳.** 앞으로 기존 React 프로젝트들의 보안 점검과 수정 요청이 늘 것이라는 전망
- **무엇이 노출되나**
  - 요청 페이로드는 SSL(HTTPS)로 암호화되어 전송됨. "페이로드가 노출된다"라고 말하면 틀린 말
  - 문제는 **응답**. 필요한 것보다 많은 값을 브라우저로 내려 주면, 개발자 도구에서 구조가 다 보임
  - 해결
    - API를 서버 뒤로 숨기기: Next 서버 액션, 또는 Vite에 Node(Express) 서버를 붙이기
    - API를 **필요한 값만** 주도록 설계하기
    - 더 하려면 암호화
- React를 쓴다면 **반드시 보안 정책**을 넣어야 함. 면접에서 기술 선택을 말할 때는 근거를 들어 설명하기
- React는 라이브러리라 "React로 개발"이라고 해도 Vite, React Router 같은 프레임워크를 따로 골라야 함
- 강사님 방향
  - 불필요한 상태 관리를 줄이고, **코드 양으로 할 일을 구조로 해결**하는 것. 만 줄을 구조로 천 줄로 줄이는 식
  - Next가 답이라는 뜻은 아님. 다만 채용 시장에 Next 개발자 수요가 늘고 있다는 전망
- **풀스택으로 가는 길**: Node.js를 공부하고, 이번에 쓴 Prisma에 DB를 붙여 API를 직접 만들 수 있으면 풀스택
  - 예: 채팅은 MongoDB+Prisma로, 정형 데이터는 Spring에서 가져오기 → DB 두 개를 다뤄 본 프로젝트가 됨
- 네트워크 탭에서 304 같은 300번대 응답(캐시)도 보면서 공부하라고 추천

### 4. 월요일 채팅 — 데이터 설계부터
**누가 주체인가**
- "보내는 사람과 받는 사람"으로 나누면 애매함: 보낸 사람도 받는 사람이 되고, 여러 명이 대화하면 더 복잡해짐
- **채팅방(Room)**을 주체로 두고 사람과 메시지를 방에 속하게 하면, 1대1이든 100명이든 같은 구조가 됨
- 메시지는 **누가 썼는지만** 있으면 됨. 나머지는 모두 읽는 사람

```
ChatRoom ── members: [A, B, C ...]
Chat     ── roomId, userId(누가), message, createdAt(언제), type
```

**화면**
- 말풍선 컴포넌트(`ChatItem`) 하나로 처리함: 내 것이면 오른쪽, 남의 것이면 왼쪽에 프로필 사진을 붙임. 컴포넌트가 `userId === 나`로 스스로 판단
- 동시에 오는 메시지는 없으니 **시간순으로 한 줄씩** 쌓으면 됨. 채팅은 아래가 최신이라, 위로 스크롤하며 옛 메시지를 봄

**메시지 종류는 `type` 하나로**
- 글, 사진, 영상, "OO님이 들어왔습니다" 같은 시스템 메시지도 모두 채팅 한 줄. 카카오톡도 한 줄에 두 개가 오지 않음
- `type`이 `message`면 글, `image`면 이미지 컴포넌트, `video`면 영상 컴포넌트, `system`이면 시스템 메시지. 종류별로 따로 받아 프론트가 조합할 필요가 없음

**읽음 처리**
- 안 읽은 사람 수 = 지금 방에 들어와 있지 않은 사람 수
- 방을 나간 시각(탈퇴가 아니라 화면을 떠난 시각) 이후 쌓인 메시지가 그 사람의 안 읽은 개수
- 들어오면 그 사람의 안 읽은 개수를 0으로 만들고, 해당 메시지들의 안 읽음 수를 1씩 줄임
- "모두 읽음 처리" API는 안 읽은 목록을 한꺼번에 읽음으로 바꾸거나 0으로 리셋하는 것
- 🔗 오늘 알림 코드와 같은 생각: `Notification.readAt`(null이면 안 읽음), `count({ readAt: null })`로 배지 숫자, `markAllRead`는 `readAt`이 빈 행만 지금 시각으로 바꿈

**프론트가 신경 쓸 것 = 이벤트가 생기는 시점**
- **나감**: 나가기 버튼, X 버튼, 창 닫기, 컴퓨터 끄기, 웹소켓 끊김, 브라우저 닫힘 감지(BOM), 앱을 내려놓음(백그라운드). 소켓은 연결되어 있어도 보고 있지 않으면 나간 것
- **들어옴**: 채팅 목록에서 방을 클릭, 소켓 연결
- 어디에 걸지는 선택이고 여러 군데 걸어도 됨. "방 탈퇴"는 나감과 다른 기능
- 🔗 오늘 `NotificationStream`이 `visibilitychange`로 탭이 숨으면 연결을 닫는 것과 같은 감지 방법
- 웹소켓은 실시간이라 먼저 보낸 순서대로 쌓임

**더 나아가면**: 입력 중 표시, 이모티콘 반응, 파일·코드 첨부, 투표, 화상 채팅. API가 다 있으니 프로젝트 목표를 크게 잡아도 된다고 함. 마크다운은 채팅 말고 위키에만 있음

- 웹소켓은 백엔드가 설치하고 만들 것이 많아서 싫어함. 그래도 프론트가 만들 수는 없으니 요청해야 함
